# Поддержание проектной документации в RAG

## Желаемое поведение

RAG должен отражать актуальные `README.md` и `project/docs/**/*.md`: изменённая версия
переиндексируется, удалённый/переименованный файл убирается из управляемого набора,
неизменённые файлы повторно не обрабатываются. Остальные пользовательские документы
и индексы не затрагиваются.

## Реализация

Backend запускает синхронизацию сразу после `ApplicationReadyEvent`, а затем
периодически сканирует только `README.md` и `project/docs/**/*.md`. Настройки: `RAG_PROJECT_DOCS_ENABLED`,
`RAG_PROJECT_DOCS_ROOT`, `RAG_PROJECT_DOCS_OWNER`, `RAG_PROJECT_DOCS_INITIAL_DELAY_MS`,
`RAG_PROJECT_DOCS_INTERVAL_MS`. По умолчанию синхронизация включена, корень — текущая
рабочая директория, владелец — `vlad`, периодический интервал — 60000 мс; начальная
задержка scheduler — 10000 мс (не задерживает первый запуск после готовности приложения).
При `RAG_ENABLED=false` синхронизатор отключён.

Хеши и active/pending версии хранятся в `rag.project_document_sync` (Flyway V6).
Каждый файл загружается как документ Markdown и индексируется структурно. При
успешном завершении новый индекс активируется, а старая управляемая версия и её
индексы удаляются. При ошибке индексации предыдущая версия остаётся доступной.
Удалённый или переименованный файл очищается только после полного успешного обхода.

Обычные документы пользователя не входят в manifest и не удаляются. Ограничения:
один файл до 2 MiB, весь набор до 20 MiB. Symlink не индексируются; список источников
фиксирован и не включает `.env`, `.git`, `target`, `node_modules`, build output и другие
каталоги. Синхронизатор рассчитан на один backend-инстанс.

## Ограничения и гарантия сохранности

Синхронизация ведёт отдельный manifest в `rag.project_document_sync`, связанный с
профилем-владельцем, и управляет только документами, перечисленными в manifest.
Сканируется только allowlist:

1. `README.md`
2. `project/docs/**/*.md`

Не следовать symlink за пределы корня checkout; ограничить общий размер и допустимые
расширения; исключить `.env`, секреты, `.git`, `target`, `node_modules`, бинарные
артефакты, пользовательские файлы и generated build output.

Алгоритм идемпотентной синхронизации:

1. Снять snapshot файлов и hash без изменения индекса.
2. Изменённые/новые файлы извлечь как UTF-8 Markdown и проиндексировать как pending
   версии; ошибки оставляют предыдущую успешную версию доступной.
3. Переключить manifest на новый document ID после успешной индексации.
4. Удалить только управляемые документы, путь которых отсутствует в актуальном manifest;
   выполнить это после успешного сканирования всего источника, не после частичного
   обхода/ошибки диска.
5. Повторить периодически и при старте, с единственным worker/lock для одного JVM.
   Логировать только path/hash/status/counts, не содержимое документа.

Профиль `vlad` должен существовать. Для production задайте `RAG_PROJECT_DOCS_ROOT` на
checkout с README и `project/docs`; при проблеме обхода прежний индекс сохраняется.
После первого старта дождитесь фоновой индексации в RAG UI/статистике.

## Приёмочные проверки

- Новый Markdown появляется как управляемый документ проекта после синхронизации.
- Повторный запуск без изменений не дублирует document/index.
- Изменение файла даёт новую индексированную версию; старые chunks не попадают в
  retrieval после атомарного переключения.
- Удаление/rename убирает только соответствующую запись проекта.
- Ошибка чтения/embedding/DB не удаляет последнюю рабочую версию.
- Пользовательские документы из других namespace неизменны.
- Путь не может выйти за корень checkout; secrets не включаются.
