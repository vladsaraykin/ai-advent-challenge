# HTTP API и MCP

Все `/api/**` маршруты требуют HTTP Basic Auth, кроме регистрации. Контроллеры
используют имя аутентифицированного профиля как владельца и изолируют его данные.

## Основные API-группы

- `POST /api/auth/register`, `GET /api/auth/me`, `GET|PUT /api/profile` — профиль.
- `/api/agents`, `/api/agents/{agentId}/chats` — агенты, чаты, ветки и история.
- `/api/agents/{agentId}/chats/{chatId}/task` — рабочая память и переходы этапов.
- `/api/agents/{agentId}/memory` — долговременная память с отдельным подтверждением.
- `/api/harness/agents/{agentId}/chats/{chatId}` — история, настройки, потоковые
  сообщения, ожидание MCP approval, статус запроса и usage.
- `/api/rag/documents` — загрузка/просмотр документов пользователя; `DELETE /api/rag/documents/{id}` удаляет документ владельца вместе с индексами.
- `/api/rag/documents/{document}/indexes` — запуск и просмотр индексации.
- `/api/rag/indexes/{run}/chunks` — просмотр чанков индексного запуска.
- `/api/harness/knowledge/stats` — статистика индекса текущего профиля.
- `GET /api/mcp/servers` — discovery MCP-серверов и инструментов без выполнения.
- `GET /api/health/dependencies` — статусы подключённых зависимостей.

Для полного набора параметров и SSE событий смотрите контроллеры `agent/api`,
`harness/api`, `rag/api`, `mcp/api` и `health/api`. Этот документ описывает публичную
карту маршрутов, но не заменяет DTO/схемы в исходном коде.

## Рабочая память и возврат к выполнению

По умолчанию все агенты используют мягкий режим: lifecycle.mode: advisory.
Память и этапы — справочная информация, а не допуск к выполнению задачи. Уточнения
идут в чате обычными сообщениями. Требования, решения и открытые вопросы не блокируют
переходы или MCP, работа разрешена из Planning и Done без нового чата. Этапы можно
отмечать кнопками по желанию; LLM не меняет их самостоятельно.
Явная пауза, права владельца, read-only checkpoint, инварианты, разрешения MCP,
ограничения записи и запрет повтора неизвестного результата остаются обязательными.
Ошибка отдельного помощника извлечения вопросов не уничтожает готовый ответ:
прежние вопросы сохраняются, известная usage учитывается.

Ниже описан строгий учебный режим lifecycle.mode: strict (включается в YAML агента).

Этапы: Planning (`REQUIREMENTS`) → Execution (`DESIGN`) → Validation (`REVIEW`)
→ Done (`DONE`). Текстовое «подтверждаю» в чате этап не меняет.

Служебное «Пожалуйста, подтвердите этот план или внесите правки» не является
уточняющим вопросом: подтверждение выполняет кнопка. Backend отфильтровывает такие
пункты при обновлении/извлечении памяти и очищает ранее сохранённые служебные вопросы
при подтверждении этапа. Настоящие вопросы о содержании задачи остаются блокирующими.
Цель не заменяет требования: если их словарь пуст, используйте «Добавить требования»,
внесите критерии из своего задания и сохраните задачу. Приложение не выдумывает
требования и не разрешает переход с пустыми требованиями.

- «Изменить данные задачи» сохраняет цель, требования, ограничения, решения и вопросы.
  На Execution кнопка «Зафиксировать решения» открывает тот же редактор. Заполните
  «Подтверждённые решения» (JSON-словарь строк) и нажмите «Сохранить задачу».
  Сохранение решений само по себе не завершает задачу; долговременная память
  и настройки чата для этого не требуются. Изменение требований возвращает Planning.
- «Подтвердить требования» переводит в Execution; «Передать на проверку» — в Validation.
- «Подтвердить завершение» открывает отдельное подтверждение: завершайте только
  когда фактический результат выполнен и проверен. Это не согласование плана,
  не сохранение памяти и не разрешение MCP-инструмента.
- В Validation и Done доступна «Вернуть в выполнение»:
  `POST /api/agents/{agentId}/chats/{chatId}/task/return-to-execution`, JSON `{"version":N}`.
  Она возвращает текущую задачу в Execution, не очищая историю, решения, память и usage.
  На паузе сначала нажмите «Продолжить задачу». Возврат не выполняет MCP автоматически.

Backend проверяет владельца, агент, версию памяти, read-only checkpoint и блокировку
генерации. При устаревшей версии — HTTP 409; обновите память. Новая задача/ветка
не открывается автоматически, LLM не может выполнять переходы вместо пользователя.

## Команда `/help` в чате

Введите `/help` и вопрос, например `/help Где описана структура backend?`. Команда
использует только завершённые индексы README и Markdown-файлов из `project/docs`,
принадлежащие настроенному профилю `RAG_PROJECT_DOCS_OWNER`. Она работает независимо
от переключателя пользовательского RAG в чате; обычные сообщения продолжают
подчиняться настройкам чата. Ответ проходит ту же серверную проверку источников и
дословных цитат, что и прочие RAG-ответы. Если документация ещё не проиндексирована
или не содержит релевантных сведений, ассистент должен отказаться от догадки.

Синхронизация документации запускается при старте приложения и периодически. После
изменения README или `project/docs` дождитесь завершения индексации; статус и детали
видны во вкладке RAG. Команда сохраняется в истории чата, но не меняет память задачи
или этап workflow.

## MCP подключения

MCP client настраивается в `spring.ai.mcp.client` файла `application.yml`.
Текущие bundled подключения:

- `project-git` — локальный read-only STDIO MCP-сервер для текущей ветки и списка
  отслеживаемых файлов. Checkout задаётся `MCP_PROJECT_GIT_ROOT` (по умолчанию `.`).
- `project-files` — поиск и чтение файлов, подготовка diff и сохранение Markdown.
  Команда `/files <цель>` использует живой checkout вместо RAG; подробнее:
  [файловый ассистент и два сценария](project-files-assistant.md).
  После завершённого `/files` обычные сообщения того же чата продолжают файловый режим.
  `/chat <вопрос>` завершает его и возвращает сохранённые RAG/MCP-настройки.
- `filesystem` — STDIO Node process `@modelcontextprotocol/server-filesystem`, корень
  задаётся `MCP_FILESYSTEM_ROOT`; выдавайте только необходимые каталоги.
- `excel` — STDIO команда `uv`, рабочая директория задаётся `MCP_EXCEL_DIRECTORY`.

Вызов инструмента не выполняется при простом discovery: фактическое исполнение
требует разового одобрения точных параметров либо явного постоянного разрешения
инструмента для этого чата. На чат можно выбрать не более
восьми MCP-серверов; неоднозначные имена инструментов отклоняются. MCP не нужно
открывать через публичный KeenDNS.

Для задания Day 31 минимальным безопасным дополнением будет read-only MCP tool,
возвращающий git branch. В настройках чата включите MCP и выберите `project-git`.
После этого запросы о текущей ветке (например, «Получи текущую git-ветку» или
«Какая сейчас ветка?») автоматически идут в MCP-only маршрут: RAG и его цитатная
валидация не запускаются, а ответ показывается только после результата
`get_current_branch`. Вопросы о структуре проекта используйте с `/help`; они ищут
документацию через RAG и при необходимости могут обратиться к `list_project_files`.
Оба MCP-вызова показываются на подтверждение; read-only git-инструменты доступны
на любом этапе задачи, но выполнение без разового или сохранённого разрешения запрещено. Сервер не
принимает shell-команды/пути от модели, не меняет checkout и исключает чувствительные
имена файлов.

`POST .../requests/{id}/approval/stream` принимает `callId`, `allow` и необязательный
`remember` (default false). `remember:true` допустим только с `allow:true`: разрешение
изолировано по владельцу, чату, серверу, инструменту и hash его схемы/описания. Оно
распространяется на любые следующие параметры, но не отменяет выбор MCP-сервера,
паузу, этапы в строгом режиме, настраиваемый бюджет вызовов и запрет повтора `UNCERTAIN`/отклонённых действий.

По умолчанию запрос может выполнить 256 различных MCP-вызовов, а одна генерация —
1024 обращения к callback, включая чтение кеша и отказы. После 24 вызовов работа
продолжается в той же цепочке модели с уже полученными результатами, без перезапуска
и повторного исполнения успешных действий. Счётчик различных вызовов хранится в БД
и сохраняется при подтверждениях и перезапусках; кеш доступен даже при исчерпанном
бюджете. При исчерпании бюджета новый инструмент не запускается: модель получает
инструкцию завершить ответ с явным списком выполненного и незавершённого. Если она
продолжает вызывать инструменты, срабатывает жёсткая защита callback. Таймауты и
ограничения контекста по-прежнему действуют; завершение произвольной задачи не гарантируется.
`GET .../tool-permissions` возвращает разрешения текущего владельца для чата;
`DELETE .../tool-permissions?server=...&tool=...` отзывает одно разрешение. Уже начатый
вызов отзыв не отменяет. Изменение реализации/root без изменения схемы автоматически
не определяется: после изменения конфигурации доверенного MCP пересмотрите разрешения.
Никакие вызовы discovery или модель сами не могут выдавать разрешения.
## AI-ревью PR (день 32)

`POST /api/reviews` принимает фиксированный snapshot PR (UUID, repository, номер,
base/head SHA, title, список файлов с patch и content). Использует управляемый RAG
аутентифицированного профиля и возвращает проверенные findings, sources, metrics и Markdown.
`GET /api/reviews/{id}` читает статус/результат только владельца. Подробный контракт,
ограничения и GitHub Actions — [code-review.md](code-review.md).
