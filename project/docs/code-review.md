# День 32: автоматическое ревью собственного PR

## Поток

GitHub Actions → diff и изменённые файлы GitHub API → аутентифицированный
`POST /api/reviews` → embedding → поиск в управляемом RAG текущего профиля → reranker →
агент `code-reviewer` → проверка JSON, строк diff и цитат → PostgreSQL → комментарий PR.

Отчёт содержит три раздела: потенциальные баги, архитектурные проблемы, рекомендации.
Каждое замечание указывает файл, сторону diff (RIGHT — новая версия, LEFT — старая),
номер изменённой строки, её дословный фрагмент и предлагаемое исправление.
`baseSha` — merge base веток (база трёхточечного PR diff), `headSha` — коммит PR;
изменение вершины целевой ветки также проверяется перед публикацией.
Архитектурные замечания требуют цитаты RAG; сервер проверяет её происхождение.
Смысловую корректность вывода оценивает человек. Модель не запускает тесты и команды.
В этом сценарии MCP-инструменты модели не предоставляются.

## Первый запуск

1. Запустить обновлённый backend с обычными PostgreSQL, OpenAI, embedding и reranker
   настройками. Flyway автоматически создаст `rag.code_reviews` (V7).
2. Для проекта оставить `RAG_PROJECT_DOCS_ENABLED=true`, `RAG_PROJECT_CODE_ENABLED=true`,
   `RAG_PROJECT_DOCS_OWNER=vlad`, а `RAG_PROJECT_DOCS_ROOT` направить на checkout.
   Дождаться завершения индексации: код добавляется в существующий RAG вместе с README
   и `project/docs`; очередь ограничена, первоначальный проход может занять несколько
   периодических циклов. RAG во время PR не загружается с нуля.
3. В GitHub → Settings → Secrets and variables → Actions добавить secrets:

   | Secret | Значение |
   |---|---|
   | `AI_REVIEW_API_URL` | Полный доступный runner адрес, например `https://chat.example.ru/api/reviews` |
   | `AI_REVIEW_USERNAME` | `vlad` — профиль, которому принадлежит проектный RAG |
   | `AI_REVIEW_PASSWORD` | Пароль этого профиля, хранится только в GitHub Secrets |

4. Отправить эти изменения в основную ветку. Workflow и automation script должны быть
   в базовой ветке **до открытия тестового PR**.
5. Создать собственную feature-ветку, внести небольшое изменение и открыть PR на основную
   ветку своего репозитория. В Actions появится `AI code review`, результат — комментарий
   `AI-ревью PR #…` и Job summary. Новый коммит запускает новое ревью и обновляет комментарий.
   Публикация комментария не является approve и не разрешает merge автоматически.

По умолчанию используется GitHub-hosted `ubuntu-latest`: backend должен быть доступен
этому runner по HTTPS. При backend только на домашнем Mac можно зарегистрировать
отдельный self-hosted runner с доступом к приложению, задать repository variable
`AI_REVIEW_RUNNER=self-hosted` и secret `AI_REVIEW_API_URL=http://127.0.0.1:8080/api/reviews`.
Loopback подходит только при runner и backend на одной машине. Node.js 20+ обязателен.
Открывать Ollama, PostgreSQL и OpenAI-ключ для runner не требуется.
Если Nginx стоит перед backend, для `/api/reviews` нужен `proxy_read_timeout 700s`:
ответ синхронный, retrieval и генерация могут занять несколько минут.

## Область доступа и ограничения

Workflow использует `pull_request_target` с проверками: PR не draft, его ветка находится
в этом же репозитории, автор — владелец репозитория. Checkout выполняется только для
доверенного базового коммита. Исходники PR читаются как данные через GitHub API,
не устанавливаются и не выполняются. Эти ограничения соответствуют сценарию
«ревьюим свои PR на самих себя», внешние PR автоматически не обрабатываются.

Доступ `GITHUB_TOKEN`: contents read / pull-requests write. Backend использует
существующий HTTP Basic и ищет RAG исключительно по аутентифицированному профилю.
Поиск ограничен активными документами `rag.project_document_sync`, а не личными PDF
пользователя. Дополнительно сервер проверяет разрешённый `AI_REVIEW_REPOSITORY`.
Содержимое diff, кода, ответы модели и секреты не выводятся в operational logs.

Лимиты: до 40 изменённых файлов, суммарно до 120000 символов путей + полного diff + дополнительного контекста,
до 12 замечаний, одна генерация ревью одновременно. Сначала резервируется место для всех
путей и полного diff; если уже они превышают лимит, PR отклоняется с предложением разделить
изменения. Diff не обрезается. Остаток распределяется между файлами: максимум 6000 символов
дополнительного контекста на файл. Небольшой файл передаётся целиком с меткой FULL FILE;
для большого выбираются hunks с пятью окружающими строками, пересечения объединяются.
Метка PARTIAL FILE CONTEXT явно предупреждает о пропущенных строках, L123 задаёт номер
строки; обрезанный префикс длинной строки помечается отдельно. При отсутствии бюджета
content пуст: отсутствие контекста не означает отсутствие реализации. GitHub-файл для
сбора контекста читается до 1 MiB. Количество добавлений/удалений patch сверяется
с GitHub metadata. Бинарные файлы без текстового diff перечисляются как непроверенные;
если в PR нет текстового diff, ревью не запускается. RAG использует существующие candidate-K,
threshold, final-K и бюджет чанков. Сбой RAG/reranker или провал проверки цитат прерывает
ревью без публикации неподтверждённого текста.

Retrieval делает не более трёх коротких запросов: до двух групп по четыре имени
изменённых компонентов (сначала Java backend, затем UI; тесты исключены) и тему PR.
Учитываются первые восемь уникальных имён компонентов, до 40 символов каждое;
тема ограничена 240 символами. Raw diff и imports в поисковый запрос не входят:
reranker использует лишь первые 96 токенов query, и длинный diff искажал поиск.
Каждый запрос проходит embedding, поиск по тому же профилю и reranker; дубликаты
chunk UUID объединяются по максимальной оценке. Затем применяется общий threshold,
final-K и единый бюджет контекста, без fallback при ошибке зависимости.
Оценка reranker — не вероятность корректности ответа. Полный diff для основного
ответа не сокращается. При отсутствии кода остаётся поиск по теме PR.
Все query короче HTTP-лимита reranker в 4000 символов.
Лог `review_retrieval_completed` содержит requestId, числа документов/запросов/кандидатов,
число выбранных чанков, maxScore, threshold и счётчики SELECTED/THRESHOLD/BUDGET/TOP_K/INVALID
(только присутствующие причины), но не текст query или документов.
Коды `review_embedding_failed` и `review_reranker_failed` различают зависимости;
в логах указывается полный класс исключения без upstream body и текста запроса.

RAG — актуальный индекс checkout сервера, не гарантированный снимок base SHA PR.
Для новых изменений истиной служит diff с зафиксированными base/head SHA; модель получает
полный diff и ограниченный контекст изменённых текстовых файлов. Источники RAG и chunk UUID перечислены
в отчёте. При обновлении PR до окончания генерации старое ревью не публикуется.

## API, хранение и повторы

`POST /api/reviews` принимает JSON:

```json
{
  "requestId": "157ae27c-2eb1-4f66-b44d-b6384588b146",
  "repository": "vladsaraykin/ai-advent-challenge",
  "pullNumber": 1,
  "baseSha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "headSha": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "title": "Исправление сохранения ответа",
  "files": [{"path": "src/Example.java", "status": "modified", "patch": "@@ -1 +1 @@\n-old\n+new", "content": "new"}]
}
```

Ответ: `id`, repository/PR/base/head, `findings`, RAG `sources`, метрики провайдера,
`usageIncomplete`, готовый `markdown`. `GET /api/reviews/{id}` возвращает статус и результат
только владельцу. Статусы: RUNNING, COMPLETED, FAILED, INTERRUPTED. Перезапуск backend
помечает незавершённые попытки INTERRUPTED; автоматического повторного платного вызова нет.

`rag.code_reviews` сохраняет snapshot запроса, hash payload, источники, известный расход
и проверенный результат. Метрики записываются **до проверки** ответа: потраченные токены
не теряются при неверной цитате/JSON. Отсутствие метрик отмечается `usage_incomplete`.
Повтор того же UUID и payload возвращает готовый результат без нового вызова модели.
UUID с другими данными отклоняется; RUNNING/FAILED/INTERRUPTED нельзя незаметно переиграть.
GitHub `run_id + run_attempt` задаёт стабильный UUID попытки. Явный Re-run jobs создаёт
новую попытку и может повторно расходовать токены.

## Конфигурация агента и проверки

`src/main/resources/review-agents/code-reviewer.yaml` задаёт prompt, 8192 выходных токенов,
timeout 240 секунд и лимит 200000 символов provider context. Модель, reasoning и цены
наследуются из server-owned `agent-defaults.yaml`. Это отдельный pipeline-агент;
его JSON-контракт не добавляется в меню обычного чата. Внешний YAML задаётся отдельно
через `AI_REVIEW_AGENT_LOCATION`; обычный `AGENT_CONFIG_LOCATION` на ревью не влияет.

Автоматические проверки без внешней модели:

```bash
node --test automation/review-pr.test.mjs
mvn test
```

Проверяются контекст RAG, изоляция профилей, строки добавления/удаления, вымышленные цитаты,
сохранение расхода при отказе, идемпотентность, wiring Spring, неполные patch, смена SHA
и обновление комментария. Фактический запуск GitHub Actions требует настроенных secrets
и работающего backend с готовым RAG.
