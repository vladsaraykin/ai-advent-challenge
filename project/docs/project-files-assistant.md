# День 34: файловый ассистент, worktree и GitHub PR

## Назначение и запуск

`/files <цель>` — работа с живыми файлами через MCP, не RAG. Ассистент сам выбирает
поиск, связанные файлы и изменения. Для записи выберите в чате оба сервера:
`project-files` и `project-git`. Без Git остаётся только чтение исходного checkout.
Запись, проверки и GitHub доступны только аутентифицированному профилю `vlad`.
Универсальный filesystem в этом режиме не предоставляется модели.

```bash
export MCP_ENABLED=true
export MCP_PROJECT_FILES_ROOT="$PWD"
export MCP_PROJECT_GIT_ROOT="$PWD"
export RAG_PROJECT_DOCS_ROOT="$PWD"
npm ci --prefix mcp
gh auth status
mvn spring-boot:run
```

Оба root должны указывать на один checkout. Для JAR задайте также абсолютные
MCP_PROJECT_FILES_ENTRYPOINT/MCP_PROJECT_GIT_ENTRYPOINT с установленными mcp/node_modules.
Нужны Git и gh CLI на машине backend; GitHub account — `vladsaraykin`, origin —
`git@github.com:vladsaraykin/ai-advent-challenge.git` либо HTTPS этого же репозитория.
Ключи/токены остаются на сервере. Проверки требуют Maven/npm и подготовленных
зависимостей в рабочей копии; отсутствующие зависимости не считаются успешным тестом.

## Рабочая область задачи

Первый `project_workspace_create` получает origin/main и создаёт ветку
`ai/task-<chatId>` в `data/project-workspaces/<chatId>`. Это отдельный Git worktree:
основная ветка запущенного backend и её незакоммиченные изменения не затрагиваются.
Незакоммиченные изменения основного checkout не копируются в задачу.
Один чат — одна область; новый чат/ветка диалога получает другой ID, не копирует файлы.
Корень области не принимается от модели: backend заменяет workspaceId ID текущего
чата. Выбранные серверы и режим фиксируются в snapshot запроса.

Метаданные, ветка, base/head SHA, состояние проверок и ссылка PR хранятся в
`rag.project_workspaces`; разрешения и результаты — в существующем PostgreSQL ledger.
Чтения включают backend revision, которая изменяется после записи/проверок и известных
отказов по предусловиям. Это предотвращает повторную выдачу старого read/search/status
после правки. SHA256 и treeHash дополнительно проверяют реальные файлы перед действием.
После перезапуска область восстанавливается из БД и Git. Удаление чата не удаляет
worktree, ветку и recovery metadata автоматически. Оператор обслуживает их отдельно.

После `/files` следующие сообщения продолжают файловую задачу. `/chat` или `/help`
выводят из режима; постоянные RAG/MCP-настройки не перезаписываются. Старый failed
request сохраняет свой snapshot: для новых настроек отмените его и отправьте новый
запрос, не пытайтесь автоматически повторить запись с неизвестным результатом.

Advisory workflow не требует ручного заполнения требований/решений в JSON-панели.
Существенные уточнения — в чате. Явная пауза, владелец, read-only checkpoint и approval
проверяются всегда; opt-in strict mode сохраняет ограничения этапов.

## Инструменты

| MCP | Инструменты |
|---|---|
| project-files | `project_list_files`, `project_search_text`, `project_read_files` |
| project-files | `project_preview_edits`, `project_apply_edits` — уникальные точечные before/after с SHA256; большой файл не заменяется его усечённым фрагментом |
| project-files | `project_create_file`, `project_rename_file`, `project_delete_file` — создание каталогов/текста, переименование без перезаписи, удаление одного файла |
| project-files | `project_preview_document`, `project_write_document` — совместимые операции полной замены небольшого документа |
| project-git | `project_workspace_create`, `project_git_status` — область, общий diff, treeHash |
| project-git | `project_run_checks` — backend-test, frontend-test, frontend-build; фиксированные mvn test / npm test / npm run build |
| project-git | `project_git_commit` — commit содержимого, проверенного по treeHash |
| project-git | `project_git_push`, `project_git_create_pr` — точный head commit, только task branch в origin, обычный PR в main |
| project-git | `project_git_remote_status` — remote SHA/существующий PR для проверки неопределённого результата без повторной записи |
| project-git | `get_current_branch`, `list_project_files` — совместимое чтение текущего проекта/задачи |

Границы: текстовый файл до 128000 байт, чтение 1–5 файлов по 6000 символов с offset,
поиск literal/case-sensitive с ограничением вывода и `truncated`. Новые файлы до 8000
символов в одном вызове, затем можно точечно дополнять. Путь относительный, без
traversal, symlink/hardlink, секретных имён, .git, data/backups, node_modules, target,
dist. Поддерживаются .github/workflows и .gitignore. Остальные скрытые пути закрыты.
Git status/commit отказываются от изменённых небезопасных/бинарных файлов; общий diff
ограничен 40000 символами, задачи — 200 изменёнными и 100 новыми файлами.
Фильтр имён не является DLP: не помещайте секреты в обычные исходники/документы.

## Разрешения и ошибки

Discovery не выполняет действия. Каждый реальный вызов требует точного разового
approval либо явно выданного разрешения конкретному инструменту этого чата.
Исключения: **удаление файла, push и создание PR всегда подтверждаются отдельно**.
Для них remember:true отклоняется и ранее выданные grants не применяются.
Push отправляет явно указанный expectedHeadSha (не изменяемый HEAD), проверяет чистый
worktree и remote; PR дополнительно проверяет remote SHA, account gh, фиксированные
head/base/repository и существующий open PR. После создания/обнаружения PR повторно
проверяются его head commit, ветки и отсутствие draft; гонка refs не выдаётся за успех.
Нет merge, force-push, reset, amend или удаления веток. В commit не попадают
посторонние изменения основного checkout. Git hooks при служебных командах отключены.

Ожидаемые отказы до изменения (например stale hash или неоднозначная замена)
возвращают operationRejected:true, saved:false — модель может перечитать файлы и
исправить параметры. Неопределённые результаты записи/сети остаются UNCERTAIN;
автоматический повтор запрещён. Проверьте Git/status/remote/PR перед восстановлением.

Проверки: ограниченное окружение без ключей провайдера, паролей БД и GitHub;
отдельный HOME, лимит 120s и остановка группы процессов на Unix. Сырые subprocess
логи не отправляются модели/UI. Результат содержит exitCode, duration, passed,
timedOut и treeHash проверенного снимка. Изменение файлов во время проверки не
считается успешной проверкой прежнего снимка. MCP_REQUEST_TIMEOUT по умолчанию 180s.
**Worktree и очищенное окружение не являются OS-песочницей**: один OS-пользователь
всё ещё имеет доступ к своим файлам/Keychain/сети. Запускайте только доверенный код;
для недоверенных PR нужен отдельно изолированный worker/container без рабочих секретов.

UI показывает область, ветку, commit, изменённые файлы, последний diff, проверку
конкретного снимка и ссылку PR. Авторизация/подтверждения выполняются backend,
не являются только визуальным ограничением. Отображённое состояние — последний
наблюдённый результат MCP, не непрерывное наблюдение за ручными правками на диске.

## Два воспроизводимых сценария

1. `/files Найди реализацию поиска диалогов: сопоставь минимум три файла UI, API и SQL. Добавь тест для найденного несоответствия и исправь реализацию. Покажи diff и результаты проверок. Пока не публикуй.`
2. `/files Изучи аутентификацию API минимум по трём файлам. Обнови project/docs/auth.md по текущему коду, проверь документ и подготовь commit. После отдельных подтверждений отправь ветку и создай обычный PR в main.`

Для анализа без изменений: `/files Найди все использования API поиска диалогов,
сопоставь UI/API/Repository и сообщи ограничения поиска. Ничего не изменяй.`

PR, созданный аккаунтом vladsaraykin в этом же репозитории, подходит под существующий
AI-review workflow. Для фактического ревью по-прежнему нужны runner, backend и Secrets.
Документы worktree не попадают в основной RAG: синхронизация смотрит исходный root.
После merge и обновления основного checkout изменения подхватит обычный sync RAG.

## Автоматическая проверка

`npm test --prefix mcp` проверяет чтение/поиск нескольких файлов, большие точечные
правки, новые документы, rename/delete/hash, сохранность main, восстановление и
два реальных STDIO-сервера. GitHub в обычных тестах замокан: нет реальных push/PR.
`node automation/postgres-tests.mjs` запускает Maven с одноразовым Docker PostgreSQL:
миграции, состояние/изоляция, кэш после правок, запрет постоянного push-разрешения,
неповторение неизвестных записей и существующие RAG/harness/review regression suites.
Frontend-тесты проверяют состояние области и обязательные разовые approvals.
Тесты без LLM не доказывают качество выбора файлов конкретной моделью — сценарии
в чате проверяются отдельно с явным согласием на стоимость OpenAI и публикацию.
