# День 33: ассистент работает с файлами проекта

## Назначение

Команда `/files <цель>` включает работу с живым checkout через MCP `project-files`.
Пользователь формулирует цель, а не последовательность открываемых файлов. Модель
сама выбирает поиск, чтение, сравнение и подготовку изменений. Это не RAG-запрос:
индекс может отставать от файлов, а серверная проверка RAG-цитат не применяется
к результату файловой операции. Обычный чат и `/help` сохраняют прежнее поведение.

Для конкретного запроса фиксируется отдельный snapshot: только `project-files`, RAG
выключен. Постоянные настройки чата, модель и reasoning не меняются. Даже если выбран
универсальный `filesystem`, в `/files` его инструменты модели не предоставляются.

## Запуск

По умолчанию lifecycle.mode: advisory. Planning/Done, пустые requirements/decisions
и нерешённые вопросы в памяти не запрещают работу с файлами. Не нужно заполнять JSON
в настройках или вручную переключать этапы: напишите цель и отвечайте на существенные
уточнения прямо в чате. При ясной цели ассистент сразу ищет и читает файлы.
Явная пауза останавливает действия, разрешения MCP остаются обязательными.
Строгий учебный workflow можно включить через lifecycle.mode: strict в YAML агента.

1. В checkout выполните `npm ci --prefix mcp`. Maven также устанавливает зависимости.
2. Запустите backend с `MCP_ENABLED=true`. По умолчанию запускается
   `node mcp/project-files/server.mjs .`; процесс должен видеть Git checkout.
3. В MCP проверьте `project-files` и пять инструментов. В чате «Личный ассистент»
   включите MCP и выберите `project-files`.
4. Напишите `/files` и цель. В мягком режиме агент начинает работу без подтверждения
   требований в панели памяти; при неясности задаёт вопрос в чате. Не оставляйте задачу на паузе.
5. Подтверждайте MCP-вызовы разово с точными параметрами либо кнопкой
   «Разрешить инструмент в этом чате» выдайте постоянное разрешение для любых следующих
   параметров этого инструмента. Его можно отозвать в настройках MCP чата. Discovery не исполняет
   инструменты. Подтверждения и результаты сохраняются в PostgreSQL; продолжение
   использует тот же request ID и кэш успешных вызовов. Неизвестная запись не повторяется.

После успешного `/files` обычные следующие сообщения этого же чата продолжают
файловый режим: «приступай» или уточнение не включает RAG обратно. Режим определяется
по последнему завершённому snapshot этого чата в PostgreSQL и восстанавливается
после перезапуска. Новые чаты/ветки его не наследуют. Для выхода используйте `/chat`
или `/help`; снятие project-files из выбора серверов тоже завершает режим для
следующего запроса. Выбранные ранее RAG/MCP-настройки не переписываются. При продолжении
ожидающего approval snapshot остаётся неизменным. UI показывает активный режим рядом с RAG.

Для запроса, уже сохранённого до исправления с `ragEnabled=true`, повтор с тем же UUID
сохраняет прежний snapshot. Он не переводится в файловый режим задним числом:
отмените незавершённый запрос и отправьте новое `/files <цель>`. Не повторяйте
автоматически записи с неизвестным результатом; сначала проверьте журнал действий.

Discovery использует стабильный ID `project-files`, даже если MCP handshake возвращает
имя `ai-advent-project-files`. Если чат сохранил прежний ID `ai-advent-project-files`,
после обновления backend заново выберите `project-files` в настройках чата. Snapshot
уже начатого запроса не переписывается автоматически. При вводе `/files` UI показывает
кнопку явного подключения сервера; выбор и отправка сообщения — отдельные действия.
Вкладка MCP показывает каталог подключений, а не список разрешений конкретного чата.
В логах `harness_request_received` подтверждает получение сообщения, а
`harness_request_rejected ... reason=project_files_not_selected` — отказ до генерации.
Текст сообщения в эти логи не попадает.

## Сценарий 1: найти использование API и проанализировать несколько файлов

Пример цели:

> /files Найди, как реализован поиск диалогов. Проследи путь от UI до SQL,
> сопоставь минимум три файла, укажи места использования и потенциальные несоответствия.
> Ничего не изменяй.

Ожидаемая последовательность, которую выбирает ассистент:
`project_list_files` → `project_search_text` → `project_read_files`.
В результате — пути, номера строк поиска, связь UI/API/repository и ограничения
проверки. Если search/read ограничены, модель должна это сообщить, а не объявлять
поиск исчерпывающим. Для длинного файла есть чтение следующей части через `offset`.

## Сценарий 2: обновить или создать документацию по реализации

Пример цели:

> /files Проверь реализацию автоматического AI-ревью и создай краткий документ
> project/docs/review-flow.md: входной запрос, получение контекста, проверка ответа.
> Основывайся минимум на трёх файлах реализации. Сначала подготовь diff,
> после моего подтверждения сохрани документ и проверь результат повторным чтением.

Ассистент обнаруживает файлы, читает реализацию и существующие документы, вызывает
`project_preview_document` (без записи), затем предлагает
`project_write_document` с тем же содержимым и SHA256 предыдущего чтения.
Для создания нового документа `expectedSha256=null`; существующий файл так
перезаписать нельзя. Запись требует разового approval или ранее выданного разрешения
на `project_write_document` в этом чате. Разрешение на чтение не разрешает запись.
Если пользователь изменил файл между чтением и записью, операция отклоняется:
нужны новое чтение и новый diff; при отсутствии постоянного разрешения — новое подтверждение. После записи — `project_read_files`
с одним путём и `expectedSha256` из результата записи: новый набор параметров не
возвращает закэшированное чтение старой версии и дополнительно проверяет hash.
При повторном запуске цель должна предлагать обновление, а не дубликат документа.

## Контракт инструментов и границы

| Tool | Операция |
|---|---|
| `project_list_files(prefix)` | Git-tracked и неигнорируемые текстовые файлы; до 500 путей. |
| `project_search_text(query,prefix)` | Буквальный регистрозависимый поиск, до 80 совпадений с путями/строками. |
| `project_read_files(paths,offset,expectedSha256?)` | 1–5 файлов; до 6000 символов каждого, SHA256 всего файла, `nextOffset`. Отсутствующий разрешённый файл возвращает `exists:false`, `sha256:null`, `content:null`, `error:file_not_found` без MCP `isError`; цепочка может продолжиться. Hash для проверки после записи — только с одним файлом; отсутствие файла при проверке hash остаётся ошибкой. |
| `project_preview_document(path,content,expectedSha256)` | Unified diff, файловая система не меняется. |
| `project_write_document(path,content,expectedSha256)` | Создать/заменить документ с проверкой версии; результат `saved:true`. |

- Корень фиксирует `MCP_PROJECT_FILES_ROOT`, по умолчанию `.`. Для JAR задайте
  абсолютные root и entrypoint; MCP-модули должны лежать рядом, с `node_modules`.
- Чтение ограничено текстовыми расширениями. Скрытые пути, имена secret/credential/password,
  каталоги data/backup/node_modules/target/dist исключены. Это фильтр имён, не DLP:
  не храните секреты в разрешённых исходниках/документах.
- Запрещены traversal, абсолютные пути, симлинки и hardlinks. Лимит чтения 128000
  байт на файл; поиск имеет общий бюджет 4 MB и флаг `truncated`.
- Запись только `README.md` и `project/docs/**/*.md`, непустой текст до 6000 символов старого/нового
  документа. Каталог должен существовать. Большие документы не заменяются целиком.
  Нет удаления, произвольного shell, записи исходников, commit или push.
- Root общий для backend: это рабочая копия проекта, не личное хранилище профиля.
  Не предоставляйте этот сервер недоверенным пользователям. Доступные инструменты
  и файлы отправляются настроенному OpenAI backend, не являются offline-режимом.
- Локальный процесс должен работать с доверенными владельцами checkout: проверки
  путей/версий не заменяют изоляцию от вредоносного процесса того же OS-пользователя.
- Сохранённая Markdown-документация попадёт в существующую периодическую RAG-синхронизацию
  только если MCP root совпадает с `RAG_PROJECT_DOCS_ROOT`; владельцем остаётся
  `RAG_PROJECT_DOCS_OWNER`. Успех записи не означает завершения индексации.

## Воспроизводимая проверка без OpenAI

`npm test --prefix mcp` создаёт временный Git-проект и проверяет два сценария:
поиск/анализ трёх файлов; preview → создание документа → readback → повтор.
Отдельный тест запускает реальный STDIO MCP и проверяет handshake, discovery,
tool schemas и операции. Также проверяются stale SHA, границы путей, симлинки,
hardlinks, ограничения размера, пагинация чтения и применимость diff через `git apply --check`.
Тесты файловых операций не используют модель; они не доказывают качество выбора
файлов конкретной LLM. Maven запускает эти тесты в фазе `test`.
