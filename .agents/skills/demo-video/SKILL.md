# Сценарий и видео демонстрации

Работай на языке пользователя. Различай два результата: сценарий для самостоятельной записи и готовое видео действий в приложении. Если запрошено видео, подготовь сценарий и доведи работу до проверенного видеофайла; если запрошен только сценарий, не запускай запись и платные запросы.

## Подготовка сценария

1. Определи демонстрируемую задачу по текущему запросу. Прочитай относящиеся к ней UI, обработчики, guards и тесты. Не переноси обещания из прежних сценариев без проверки кода.
2. Для каждого шага установи предусловия, действие, ожидаемый результат и наблюдаемое доказательство. Различай отказ на текстовый запрос к LLM и отказ детерминированного перехода по кнопке.
3. Используй [шаблон сценария](assets/scenario-template.md): отдельно **«Текст в чат»**, **«Действия в UI»**, **«Что говорить на видео»**. Если сообщение не нужно, укажи это явно. Добавь короткий текст экранной вставки для видеорежима.
4. Сценарий с LLM должен учитывать вариативность. Перед отрицательным тестом проверь фактическую память и состояние. Например, решения могут появиться ещё при сборе требований: обещать отказ по условию `decisions.isEmpty()` без проверки нельзя.
5. Если тест требует специальных данных, явно опиши подготовку в отдельном демонстрационном чате через UI. Сохраняй остальные требования: пропущенный при ручной правке пункт модель может восстановить из истории, что вызовет возврат к согласованию.
6. Речь объясняет только доказанное поведение. Наличие решений не доказывает полноту проектирования; доступность кнопки Done не доказывает успешность проверки. Отдельно обозначай семантические решения LLM и гарантии Java-кода.

## Запись видео

Для видеорежима прочитай [инструкцию записи](references/recording.md). Проверь доступные средства браузерной автоматизации, адрес работающего сервиса, способ входа и кодировщик.

- Используй отдельный профиль/чат, когда это поддержано приложением и находится в рамках запроса. Запись демонстрации допускает необходимые тестовые действия в этом профиле, но не означает разрешение на изменение чужих чатов, деплой или исправление приложения.
- Запросы к реальной модели выполняй в объёме сценария. При временной ошибке допустим один осмысленный повтор после проверки состояния и отсутствия завершённого хода. Повторная неудача — повод остановить этот шаг и объяснить ограничение, а не создавать бесконечные платные повторы.
- Показывай реальные клики, ввод, ожидание и ответы. Для демонстрации UI используй UI; прямые запросы к API годятся для диагностики, но не должны выдаваться за нажатия кнопок.
- Вставки поясняют текущий шаг и фактический результат. Не заменяй ответы модели подготовленным текстом. Редактирование DOM допускается для титров, указателя и места под титры, но не для изменения данных, ошибок или статуса приложения.
- Если ожидаемый результат не совпал с фактическим, приостанови зависимые шаги и проверь причину. Исправь сценарий или явно покажи восстановление. Не монтируй сбой так, чтобы он выглядел успешным результатом.
- Существующие разрешения пользователя учитывай; дополнительное подтверждение нужно только при недостающем доступе или расширении задачи. Этот skill не требует обязательного согласования каждого сценария или клика.

## Результат

Сохрани сценарий и MP4 в отдельной папке артефактов. В этом проекте используй `data/demo-videos/<название-записи>/`: видео не должно попасть в Git вместе с исходниками. Не перезаписывай прежние записи без запроса.

Перед выдачей проверь начало, ключевой отказ, переход и финальный кадр, читаемость вставок, отсутствие секретов, длительность и декодирование MP4. Закрой только созданный для записи браузер и свои процессы.

В финальном ответе дай ссылки на видео и сценарий, длительность, наличие озвучки и существенные отклонения от сценария. Если использовались платные запросы, укажи доступную оценку по метрикам приложения; не выдавай её за подтверждённый биллинг провайдера. Если видео не создано, прямо скажи, что готово и что помешало записи.
